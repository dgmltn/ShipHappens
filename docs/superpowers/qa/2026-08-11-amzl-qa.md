Shape notes for the follow-up (per task-6 brief, noted verbatim):
- **`predictiveDeliveryWindowDetails: null`** on this label-created parcel — the
  narrower delivery-window shape (spec/plumbing landed 2026-07-19,
  `eta-delivery-window-status.md`) has still never been observed populated for amzl.
  Needs a parcel further along its lifecycle (likely out-for-delivery) to capture the
  real shape.
- **`location: {}`** (empty object) on the sole eventHistory event — confirms the
  design-doc comment in `AmzlApiParser.kt` ("recon package's location was {}").
  `AmzlLocation`'s field names (`city`, `stateProvince`, `countryCode`) are still
  unconfirmed against a populated payload; `.render()` correctly degrades to `null`
  location for the empty case (matches the UI's generic "package location" map
  placeholder — no location chip shown, as expected).
  `progressTracker.progressMeter.milestoneList[]` (position/mileStoneType/eventSummary
  with `translatorString.localisedStringId` like `swa_rex_shipping_label_created`,
  `swa_rex_intransit`, `swa_rex_ofd`, `swa_rex_delivering_eddday`) is present but
  entirely unparsed by `AmzlApiParser` today — it's a forward-looking richer
  milestone list (with future-dated `timeElement`s per step) that a later increment
  could mine for a fuller progress bar; tolerant `ignoreUnknownKeys` means its
  presence is harmless now.
- `summary.metadata.creationDate` ("Aug 10, 2026, 10:33:15 PM") is unused by the
  parser but matches `eventHistory[0].eventTime` ("Aug 10, 2026, 10:33:20 PM") to the
  second, modulo a 5s skew — confirms both timestamps describe the same label-created
  moment and the parser's choice to use `eventHistory` for the event feed is correct.
- `shipperDetails`/`shipperBrandingDetails`/`packageMarketplaceDetail` are populated
  but unused by the parser (no product surface for them yet) — no action needed.

## Not-found path (TBA000000000001, Step 4)
- [x] Add + refresh. The API responds HTTP 200 with an in-band error — `errors:
  [{"errorCode":"TRACKING_ID_NOT_FOUND","errorMessage":"INVALID TRACKING_ID"}]` — which
  `AmzlApiParser.parse` correctly nulls out (`tracker.errors.isNotEmpty()` → return
  null → routes `Unparsed`, per the design comment "the DOM extractor owns the
  NotFound outcome"). The DOM extractor's `notFound` regex then classified the real
  page correctly: `DOM result: {"page":"notFound"}` on the very first attempt — no fix
  needed to the regex or its wording list.
- [x] `scrape DONE: 2 payload(s), NO tracking — routed=[Unparsed, NotFound]` →
  `WebViewBasedSource.track` maps this to `SourceResult.Failure(FailureReason.NOT_FOUND,
  "Amazon Logistics doesn't recognize this number")` (confirmed by reading
  `WebViewBasedSource.kt`; this message is framework-level, shared by all
  WebView-based sources, not amzl-specific code).
- **UI note (not an amzl bug):** the add-flow's headless refresh is best-effort and
  shows no failure toast (documented framework behavior — see `verify` skill: "The
  add-path refresh is best-effort and shows no failure toast"). The card is left in
  the same "never-refreshed" default state as a made-up tracking number: list row
  reads "Waiting for first update", detail screen shows a blank ETA dash and the
  first timeline step ("Label created") pre-highlighted as a generic placeholder, not
  actual scraped data. This matches existing UPS/USPS not-found behavior; there is no
  amzl-specific gap here, but it's worth flagging as a pre-existing product-level
  question (does the user ever learn "this number isn't real"?) outside this task's
  scope.

## Tracer review / DOM-fallback forcing (Step 5)
Because the API capture always wins the race on a healthy page (see above), the DOM
extractor's `page:'raw'`/`page:'notFound'` payloads never got a chance to complete a
normal scrape — the API's `RouteResult.Tracking` always completes the scrape first.
To validate the DOM selectors and not-found wording independently, `apiUrlPatterns`
was temporarily pointed at a non-matching path
(`.*track\.amazon\.com/api/QA-DISABLED-tracker/.*`), the app rebuilt/reinstalled, and
both parcels refreshed via pull-to-refresh. This is a **temporary, reverted** local
edit — `git diff` is empty after this QA session; it is not part of any commit.

DOM-forced results:
```
# TBA333593378975 (live, label-created)
DOM result: {"page":"raw","raw":{"kind":"tracker","statusText":"Label Created"}}
scrape DONE: 1 payload(s), TRACKING found — cached

# TBA000000000001 (bogus)
DOM result: {"page":"notFound"}
scrape DONE: 1 payload(s), NO tracking — routed=[NotFound]
```
- The status-headline selector chain (`#primaryStatus` → `[class*="pt-status"], …` →
  `main h1, h1`) found "Label Created" and `parseAmzlRaw` classified it to
  `LABEL_CREATED` — matching the API-derived status exactly. **No `noStatusHeadline`
  bail-out was observed; no selector fix needed.**
  Note this only validates the label-created state's markup; the selector chain is
  still unexercised against later-lifecycle headlines (out-for-delivery/delivered)
  live — the unit-test vocabulary in `AmzlWebSpecTest` covers those in isolation but
  the live DOM element matched has not been confirmed for those states.
- The not-found regex (`couldn.t find|can.t find|unable to find|invalid tracking|no
  longer available`) matched the real not-found page's body text on the first try.
  **No fix needed.**

After this test, `apiUrlPatterns` was reverted to
`.*track\.amazon\.com/api/tracker/.*`, the app rebuilt/reinstalled, and normal
operation reconfirmed (list renders both parcels correctly; `git status` clean).
